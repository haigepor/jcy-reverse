## 2. 前置：让 `/system` 可写入（核心难点）

### 2.1 现象

```
$ adb shell "su -c 'mount | grep \" on / \"'"
/dev/block/sda2 on / type ext4 (ro,seclabel,nodev,relatime,errors=panic)

$ adb shell "su -c 'mount -o remount,rw /'"
'/dev/block/sda2' is read-only          # 块设备层就拒绝，remount 无效
```

`su` 是雷电自带的（非 Magisk），权限够但**磁盘本身以只读方式挂载**。

### 2.2 定位过程（三层剥茧）

**第一层：虚拟机配置**

`vms/leidian0/leidian.vbox` 里能看到根因：

```xml
<HardDisks>
  <HardDisk uuid="{20160302-bbbb-...}" location="C:\leidian\LDPlayer14\system.vdi"
            format="VDI" type="Readonly"/>          <!-- ← 只读在这里 -->
  <HardDisk uuid="{20160302-cccc-...}" location="data.vdi" format="VDI" type="Normal"/>
</HardDisks>
```

但该文件每次启动都被重新生成（`** DO NOT EDIT THIS FILE`），**手改无效**。

**第二层：找出生成它的组件与开关键**

在安装目录全量扫描 `Readonly` 字符串，命中 `dnplycore.dll`：

```python
d = open('dnplycore.dll','rb').read()
d.find(b'<HardDisk')
# → 模板：<HardDisk uuid="{%s}" location="%ssystem.vdi" format="VDI" type="Readonly"/>
#   占位符：<my_shared_system_vmdk_xml_node/>
```

再从 `dnplayer.exe` 的 ASCII 字符串拿到全部配置键，其中唯一相关的是：

```
basicSettings.standaloneSysVmdk
```

**第三层：用 UI 资源包确认语义**

`dnresource.rcc` 其实是 **7z 包**（头 `377a bcaf 271c`），用雷电自带 `7za.exe` 解开后，`xml_playersetting.xml` 里磁盘设置是一个单选组：

```xml
<Option name="StandalonesystemOnOpt"  text="@playersetting91_disk_system_read"  group="standalonesystem"/>
<Option name="StandalonesystemOffOpt" text="@playersetting91_disk_system_write" group="standalonesystem"/>
```

语言表 `multi_language.tsv` 给出文案：

| 文本键 | 中文 | 英文 |
|---|---|---|
| `playersetting91_disk_system_read` | 共享只读（推荐） | Shared read-only |
| `playersetting91_disk_system_write` | **可写入** | Writable |

> 官方论坛印证（[ldmnq.com/forum/88215](https://www.ldmnq.com/forum/88215.html)）：
> 9.0.22 起的「磁盘共享」默认只有读权限，会导致 Xposed、抹机王等异常，需勾选「System.vmdk 可写入」。

### 2.3 结论与操作

`vms/config/leidian0.config` 中：

| 值 | 含义 | 表现 |
|---|---|---|
| `"basicSettings.standaloneSysVmdk": false` | 共享只读（**出厂默认**） | `system.vdi` 以 `type="Readonly"` 挂载 |
| `"basicSettings.standaloneSysVmdk": true` | **可写入** | 生成独立系统盘 `vms/leidian0/system.vdi`，可写 |

操作（含备份）：

```bash
cd /c/leidian/LDPlayer14
cp vms/config/leidian0.config "vms/config/leidian0.config.bak.$(date +%Y%m%d_%H%M%S)"

python - <<'EOF'
import json, collections
p = 'vms/config/leidian0.config'
d = json.loads(open(p, encoding='utf-8').read(), object_pairs_hook=collections.OrderedDict)
d['basicSettings.rootMode'] = True            # ROOT 权限
d['basicSettings.standaloneSysVmdk'] = True   # system 可写入
open(p, 'w', encoding='utf-8', newline='').write(json.dumps(d, ensure_ascii=False, indent=4))
EOF

./ldconsole.exe reboot --index 0              # 原地重启（保留窗口）
```

验证：

```bash
adb shell "su -c 'mount -o remount,rw /; touch /system/.rwtest && echo WRITE_OK && rm -f /system/.rwtest'"
# → WRITE_OK
```

> **副作用**：开启后会在 `vms/leidian0/system.vdi` 生成一份独立系统盘（≈1.87 GB，与 `LDPlayer14/system.vdi` 同尺寸），这是可写的代价。

## 3. 安装 Kitsune Mask（面具主体）

雷电 14 基于 Android 14，**只支持 Kitsune Mask（狐狸面具）**，官方版 Magisk 不适用。


## 4. 清理 su 冲突

雷电自带的 `/system/xbin/su` 会与 MagiskSU 抢 `su`，需删除（注意必须在**同一条命令内先 remount**）：

```bash
adb shell "su -c 'mount -o remount,rw /; rm -f /system/xbin/su /system/bin/su'"
# 此时 su 会消失，属正常——重启后由 Magisk 提供
```

重启后 `/system/bin/su` 重新出现（MagiskSU 提供）。

## 5. 授权 MagiskSU 给 adb shell

重启后 `su -c id` 报 `Permission denied`。原因：Magisk 的「超级用户访问权限」默认是 **仅应用**，adb（uid 2000）一律拒绝。

**必须手动改一次**（面具 App → 设置 → 超级用户 → 超级用户访问权限 → **应用和 ADB**）。

> 若之前产生过 DENY 记录：进入「超级用户」标签页 → 点 `[SharedUID] Shell` → 「撤销」，再重新请求即可。

验证：

```bash
adb shell "su -c id"
# → uid=0(root) gid=0(root) groups=0(root) context=u:r:magisk:s0
```

## 6. 安装模块（全程命令行，无需 GUI）

Kitsune 的 `libmagisk64.so` 支持 `--install-module` 与 `--sqlite`，可完全绕过 GUI：

```bash
# 关闭内置 Zygisk（Zygisk Next 会与它冲突）
adb shell "su -c \"magisk --sqlite 'SELECT * FROM settings'\""   # 先看现有键
# 注：内置 Zygisk 关闭也可在 App 设置里点掉；Zygisk Next 首次运行会提示
#     "Please disable built-in zygisk of magisk"

# 依次安装
adb shell "su -c 'magisk --install-module /sdcard/Pictures/Zygisk-Next-1.5.0-843-5217106-release.zip'"
adb shell "su -c 'magisk --install-module /sdcard/Pictures/LSPosed-v2.1.0-7769-release.zip'"
```

安装输出要点：

| 模块 | 关键输出 |
|---|---|
| Zygisk Next | `Verified bin/x86_64/zygiskd`、`lib/x86_64/libzygisk.so`、`lib/x86_64/libzn_loader.so`、`machikado.x64_32`、`Installing custom sepolicy rules`、`Done` |
| LSPosed | `extract lib/x86_64/libframework.so -> .../zygisk/x86_64.so`、`Welcome to LSPosed!`、`Done` |

**LSPosed 管理器**需单独安装（模块包内的 `manager.apk`）：

```bash
python -c "
import zipfile
z=zipfile.ZipFile('LSPosed-v2.1.0-7769-release.zip')
open('LSPosed-manager.apk','wb').write(z.read('manager.apk'))"
adb install -r LSPosed-manager.apk
```

**Shamiko 失败记录**：`Shamiko-v1.2.5-414` 在 `customize.sh` 阶段拒绝安装——

```
! Please install Magisk Canary (>27005)
```

Kitsune 版本号为 27002，低于要求。**替代方案**：使用 Zygisk Next 自带的「排除策略 / DenyList」（`/data/adb/zygisksu/`），或换更低版本 Shamiko。

重启后确认模块生效：

```bash
adb shell "su -c 'ps -A -o PID,NAME | grep -E \"zygisk|lspd\"'"
#   171 sh      sh /data/adb/modules/zygisk_lsposed/daemon
#   178 lspd    lspd
```

## 7. 部署 frida-server

```bash
adb push "tools/fs" /data/local/tmp/frida-server     # 110,754,760 B
adb shell "su -c 'chmod 755 /data/local/tmp/frida-server'"
adb shell "su -c '/data/local/tmp/frida-server --version'"      # → 17.8.2
adb shell "su -c 'nohup /data/local/tmp/frida-server >/dev/null 2>&1 &'"
adb forward tcp:27042 tcp:27042
```

验证监听：

```
tcp  0  0  127.0.0.1:27042  0.0.0.0:*  LISTEN  3021/frida-server
```

**宿主端**：系统 Python 已带 `frida 17.8.2`（与服务端版本一致，**版本必须匹配**）。

```python
import frida
dev = frida.get_device_manager().add_remote_device('127.0.0.1:27042')
print(len(dev.enumerate_processes()))          # 103
print([a.identifier for a in dev.enumerate_applications()])
# ['com.android.browser', ..., 'com.tudou.tool', 'io.github.huskydg.magisk', 'org.lsposed.manager']
```

一键拉起脚本见 `scripts/re-env/start_re_env.bat`，验收脚本见 `scripts/re-env/verify_env.py`。

## 9. 关键结论：目标 App 在 x86_64 上跑不稳

这是本次搭建中最重要的一条，直接影响后续动态分析路线。

```bash
adb shell "su -c 'dumpsys package com.tudou.tool | grep primaryCpuAbi'"
#    primaryCpuAbi=arm64-v8a
```

App 的 native 库**只有 arm64**（`libapp.so` / `libflutter.so` / `libcore.so` / `libloader.so` 等，均位于 `lib/arm64/`）。
雷电是 x86_64，只能靠 `libhoudini` 做 ARM→x86 转译，而转译层在 Dart AOT 代码上崩了。

`/data/tombstones/tombstone_01`（22:41）与 `crash_copyx86/content.txt` 记录一致：

```
Cmdline: com.tudou.tool
pid: 9372, tid: 9471, name: DartWorker  >>> com.tudou.tool <<<
signal 11 (SIGSEGV), code 128 (SI_KERNEL), fault addr 0x0

backtrace:
  #00 pc 00000000003aa43c  /system/vendor/lib64/libhoudini.so
  #01 pc 0000000000313e06  /system/vendor/lib64/libhoudini.so
  #02 pc 0000000000310ff2  /system/vendor/lib64/libhoudini.so
  #03 pc 000000000030e5ce  /system/vendor/lib64/libhoudini.so
```

| 判断 | 说明 |
|---|---|
| 环境问题？ | **否**。frida 能 spawn、能枚举 304 模块/11 线程，Magisk/Zygisk/LSPosed 均正常 |
| App 问题？ | **否**。是 x86_64 宿主 + arm64-only App 的转译兼容问题 |
| 影响 | 动态 hook 会在 `DartWorker` 线程被 libhoudini 带崩，无法稳定跑完整流程 |

**后续动态分析建议**：改用 arm64 原生环境（真机 / arm64 系统镜像模拟器 / MuMu 等带原生 ARM 支持的方案）。
静态侧（blutter / reFlutter / 已有的 `research/artifacts/blutter_out`）不受此影响。

## 10. 运维与踩坑

| 现象 | 原因 | 处理 |
|---|---|---|
| `adb devices` 显示 `offline`，`su`/`shell` 全挂 | `adb kill-server` 后 guest 端 adbd **不会自动回连** | `ldconsole reboot --index 0` 恢复；平时别随手 kill-server |
| VM 偶发卡死、adb 短暂 offline | 宿主负载导致 VM 时序滞后（`VBox.log`: `TM: Giving up catch-up attempt at a 60 002 396 959 ns lag`） | 降低并发操作密度，稍等自愈 |
| `adb install /sdcard/xxx.apk` 报 `No such file` | Git Bash 把 `/sdcard/...` 转成了 Windows 路径 | 用宿主机绝对路径，或 `export MSYS_NO_PATHCONV=1` |
| 手改 `leidian.vbox` 无效 | 每次启动由 `dnplycore.dll` 重新生成 | 改 `vms/config/leidian0.config` |
| `su -c "mount -o remount,rw /"` 报 `su: invalid option -- o` | adb shell 会重组参数，引号被吃掉 | 整体加一层引号：`adb shell "su -c '...'"` |
| App 反复闪退 | arm64 转译崩溃（见第 9 节） | 换 arm64 环境 |
