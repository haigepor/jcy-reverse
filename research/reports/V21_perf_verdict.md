# V21 性能路线裁决报告

> 日期：2026-10-06　上一版：V20_perf_options.md
> **本报告的每一行数字都来自真实执行，未执行的项明确标注。**

## 一、结论先行

V20 提出的 5 条方案，本轮逐条实测后 **3 条被自己的数据推翻**，
**1 条（基本块合并）实现并取得 3.95× 实测提速**，
1 条（编译优化）仍在验证中。

```
V19 全链路 639 块 : 24076 ms   (标定 23.6s + 解密 0.5s)
V21 全链路 639 块 :  4533 ms   (标定 4142ms + 解密 391 ms)   ← 5.3× 提升
目标:              :  1000 ms   → 仍未达成，差 4.53×
```

**问题定义（V20 修正后一直成立）**：解密本体 639 块只要 382 ms（已 <1s，
纯 Python 算术，与引擎无关），**100% 成本在标定那一次全零加密**。

## 一之二、本轮最大的发现：C 后端此前从未真正运行

修合并时挖出两个从 V19 就存在的隐藏 bug，都被「异常 → 自动回退 Unicorn」掩盖：

1. **捕获条数断言错误** → 抛异常被吞 → `_c_ready=False` → C 后端整个被关掉。
2. **`_determine_C_c` 的 iv 硬编码成 `reverse(K)`**，但标定 C 需要 `iv=全零`。

第二个症状极具欺骗性：**`CONST[639]` 全对**（CONST 只依赖 x_b，不依赖 C），
只有 `C`/`Cb` 错——很容易误判成「捕获取位错了」而查错方向。

**含义**：V19 报告里所有「C 引擎比 Unicorn 慢」的结论都不可信——
C 引擎当时根本没被调用。修掉后 C 后端 4761 ms vs Unicorn 9512 ms，**快 2.0×**。

## 二、三条路线被实测否决

### 否决 1：K 缓存 —— K 在真实流量里 100% 不复用

```
tmp_pairs.json 13 条样本 → 10 个不同 k16，无一重复
```

V20 的方案 1（修缓存键 + LRU + 增量补齐）前提是「同一 K 只标定一次」。
实测前提不成立：**每个请求都是新 K**，缓存命中率0，均摊收益 = 8930/1 = 8930 ms。

> 修正：V20 报告里「修缓存键」的零风险收益，实测为零。

### 否决 2：CONST 序列外推 —— 不是代数序列

V20 曾推测 CONST[b] 可能是某个固定映射的迭代。实测否证：

|检验 | 结果 |
|---|---|
| `C[i^j] == C[i]^C[j]`（仿射可加性） | (1,2) (1,3) (2,3) (1,4) (2,5) (3,7) **全部 False** |
| 16 条 CONST 是否有循环 | 16 unique / 16，**无重复** |

CONST 序列看起来是高熵伪随机，无代数结构 → **无法闭式外推，必须逐块跑完整链**。

### 否决 3：标定可增量续算 / 切段并行 —— 引擎内部状态不可重入

尝试从第 8 块续算：把 iv 换成 `ctd[7]`，再跑 8 块全零，与一次跑 16 块对比：

```
密文链是否一致: False
x_b 是否一致  : False
```

说明 libcore 除密文链外还有**跨块累积状态**（某个 block counter 类寄存器不随入口重置）。

**这条否决同时杀死了方案 2 的单请求版本**：
一条标定链不能切段，所以单请求 639 块**无法通过多进程并行化**。

## 三、确认成立的事实

| 性质 | 实测证据 |
|---|---|
| `CONST[b]` 是**块号的确定函数**，与 nblk 无关 | N=16 与 N=24 两次独立运行，`CONST[0:16]` 逐字节相同 |
| `CONST[0] == 全零` | 因 `x_0 = iv` 且 dummy 全零 |
| 不变式 `Cb_b == CONST[b+1]^CONST[1]` | 双后端、639 块全 True（V19 已验证） |

## 四、方案 2 的可用形态：并发吞吐池（已实现并验证）

**`calib_pool.py` / `CalibPool`** —— spawn 上下文的进程池，每 worker 一个 Unicorn 会话。

### 实测数据

**正确性**（`verify_pool.py`，64 块，随机 K）：

```
Unicorn 串行 :  1333 ms
池化首次     :  6927 ms   （含 spawn）
池化第 2 次  :  1099 ms   ← spawn 已摊销
C一致=True  rk一致=True  CONST全一致=True  Cb全一致=True
结论: PASS 池化标定与串行逐字节一致 ✓
```

**扩展性**（`bench_scaling.py`，每任务 320 块）：

```
进程数 任务数 spawn(ms) 计算(ms) ms/任务 相对1进程
     1     1        36      4099     4099     1.00x
     2     2        10      4515     2257     1.82x
     4     4        19      5532     1383     2.96x
     6     6        36      6369     1062     3.86x
     8     8        47      7706      963     4.25x
```

两个关键读数：

1. **spawn 固定开销可忽略**（10–47 ms），所以「每次新建进程」的旧模式没有这部分成本。
2. **扩展性严重亚线性**：8 进程只有 4.25×（12 核机器）。这是**内存带宽饱和**的典型特征
   ——QEMU 每条指令都要访存，多进程同时跑就把带宽打满了。

→ 池大小的最优区间是 **4–6**，代码里取 `(cpu_count)//2` 上限 8。

### 这个池解决什么、不解决什么

| | 效果 |
|---|---|
| 并发 N 个请求的总吞吐 | **提升约 2.5–4.3 倍**（N=6 时 6 任务 26084→ 6369 ms） |
| 单请求 639 块延迟 | **无改善**，仍是 8930 ms（一条链不能切段） |

已接入 `authgen_server._pool()` / `_pool_calibrate()`，
无池或异常时自动回退原有一次性子进程路径。

## 五、基本块合并（已实现并验证通过）—— `-O1` 之外的另一条路

`-fno-gcse` 实验证明编译优化救不了，但**架构层面的 dispatch 开销是可以直接消掉的**。

### 实现：`gen_engine.py --fuse`

把「顺序落到 PC+4」的连续指令（`term==False`）串成一条 C 顺序语句，
只在**基本块尾**做一次 `DISPATCH()`。trace 写入抽成 `TRACEPUT()` 宏，
块内每条指令后仍写trace（省掉的是间接跳转，不是 trace）。

**必须独立成块的 4 条安全边界**（缺一条就错）：
1. `term==True`（该指令自己 jump/return）
2. `HOOK_A1/HOOK_E/HOOK_X` 轮驱动捕获点
3. 语句含 `PC =` / `goto` / `DISPATCH(` / `return`
4. `Unimpl` 指令

### 合并效果（生成器实测输出）

```
未合并 : 25018 个基本块（每条指令一次 dispatch），源码 4255.5 KB
合并后 :  4401 个基本块，消掉 20617 次 dispatch（82.4%），源码 4095.3 KB
```

### 正确性验证（全部实测通过）

| 判据 | 结果 |
|---|---|
| 1 块 body（全零明文）vs `golden1` | **32 字节逐字节一致** |
| 128 块 body vs `golden128` | **2064 字节逐字节一致** |
| **639 块 body vs `golden639`** | **10240 字节逐字节一致** |
| **1 块 PC trace vs Unicorn 参考** | **2,180,018 条逐条完全一致** |

trace 对拍是**独立于 C 引擎**的判据（参考来自 Unicorn 全范围 hook），
比「与自己的基线比」强得多。合并没有丢任何 PC。

> 坑：`argv[7]` 不是 trace 布尔开关，而是 `TRACE_LIM` 本身（`main.c:167`）。
> 传 `"1"` 会把上限设成 1 条，trace 只记1 条就停 —— 一开始误以为合并丢了 PC。

### 性能（干净环境，同口径取最优）

| 负载 | 未合并基线 | 合并版 | 提速 |
|---|---|---|---|
| exe 128 块 | 2917 ms | **621 ms** | **4.70×** |
| exe 639 块 | 15664 ms | **3723 ms** | **4.21×** |
| **DLL 639 块标定** | 14535 ms | **3682 ms** | **3.95×** |

合并版 3682 ms **已比Unicorn 标定（8930 ms）快 2.4×**。

### 端到端（`verify_backends.py`，这是真实用户路径）

```
A 639 标定对拍 : C 4761 ms  vs Unicorn 9512 ms  → 2.0×   C/CONST[639]/Cb[639] 全一致
B 真实样本     : 一致 9 / 不一致 0 / 跳过 1
C 639 全链路   : 标定 4142 ms + 解密 391 ms = 4533 ms
```

**V19 时全链路是 24076 ms → 现在 4533 ms，整体 5.3×。
距 1000 ms 目标从「差 24倍」缩到「差 4.53 倍」。**

## 五之二、修合并时挖出的两个隐藏 bug（C 后端此前从未真正生效）

这两个 bug 从 V19 就存在，但一直被「异常 → 自动回退 Unicorn」掩盖，
表面症状是「C 引擎慢」，实际是 C 后端**根本没在跑**。

### bug 1：捕获条数断言把 C 后端静默踢回 Unicorn

`encrypt_with_x` 断言 `got != 2*nblk` → 抛异常 → `_calibrate_c` catch →
`_c_ready=False` → 后续全部走 Unicorn。

分档实测真实命中数（V21）：

```
nblk:    1    2    4    8   32  128  639
CAP_N:   2    3    5    9   33  129  640     ← nblk+1，不是 2*nblk
Unicorn: 639 块命中 1280 条，取 range(0,len,2) 得 640 条
```

**关键认识**：Unicorn 的「取偶数位」是 **QEMU TB 重译的伪影，不是语义**。
V19 把它照抄到 C 侧，而当时 C 侧恰好每块留 2 条，「偶数位」正好对上——纯属巧合。
正解：C 侧每块严格 1 次，**顺序取前 nblk 条**。
实测 `T(xs[0]) == xu[0]`、两侧 ctd 首块逐字节相同，确认顺序取正确。

### bug 2：`_determine_C_c` 的 iv 错了

`jcy_encrypt()` 把 iv **硬编码**成 `reverse(K)`，但 `C = ct ^ T(st10)` 里的
`ct` 来自 **`iv=全零`** 的那次加密（Unicorn 侧 `_determine_C` 正是如此）。

症状极具欺骗性：**`CONST[639]` 全对**（CONST 只依赖 x_b，不依赖 C），
只有 `C` 和 `Cb` 错——很容易误判成「捕获取位错了」而查错方向。

修法：DLL 新增 `jcy_encrypt_iv(k16, iv16, ...)`；`jcy_encrypt` 改为薄封装转调它；
`decrypt_e._determine_C_c` 改用 `encrypt_with_iv(K, bytes(16), bytes(16))`。

## 五之三、`-O1 -fno-gcse`（编译中，结论未定）

GCC man page 对 computed goto 的**唯一专门建议**（V19 的 13 组参数组合恰好漏了它）：

> When compiling a program using computed gotos, you may get better runtime
> performance if you disable the global common subexpression elimination pass
> by adding `-fno-gcse`.

实测：

| 参数组 | 结果 |
|---|---|
| `-O2 -fno-gcse` | `cc1: out of memory allocating 65536 bytes` |
| `-O2 -fno-gcse -fno-crossjumping` | 同上 OOM |
| `-O2 -fno-gcse --param=max-gcse-memory=64` | 同上 OOM |
| `-O1 -fno-gcse -fno-crossjumping` | 跑 17 分 52 秒后失败，无输出；重跑中 |

> `-O2` OOM 的根因是 `pass_duplicate_computed_gotos` 的 O(N²) un-factor 展开
> （25018 个 label），`-fno-gcse` 关的是 CSE 不是 goto duplication，救不了 `-O2`。
> `-O1` 不做 goto duplication，理论上可行但极慢。

## 七、本轮踩的坑（本轮共4 个，前两个极隐蔽）

**1. 捕获断言异常 → 静默回退，表面症状是「慢」而非「错」。**
`encrypt_with_x` 抛异常被 `_calibrate_c` 的 `except` 吞掉 → `_c_ready=False`
→ 整个 C 后端被关掉。**这是最危险的一类 bug**：功能全对（走 Unicorn），
只有性能异常，没有任何报错。
→ 对策：任何「后端自动回退」都必须在关闭时打日志，否则永远不会有人发现。

**2. `multiprocessing` spawn + heredoc 会假死。**
用 `py -3.12 - <<EOF` 从 stdin 喂脚本时，spawn 子进程 re-import `__main__` 会卡死，
表现为 SIGTERM / 超时 —— **看起来像性能问题，实际是脚本方式问题**，白白耗掉约 50 分钟。
必须写成真实 `.py` 文件 + `if __name__ == "__main__":` 保护。

**3. benchmark 测了同一个 DLL 两次。**
`c_engine.load(dll_path: str = DLL)` 的**默认参数在函数定义时求值**，
改模块变量根本换不掉库；加上 `_lib` 是进程级单例，第二次调用直接 return，
**根本不会 dlopen 第二个库**。第一版 `bench_fuse.py` 因此测出「合并 0.99×」的假结论。
→ 修法：`load(dll_path=None)` 内部再取 `DLL`，加 `loaded_path()` 断言，
benchmark 改成**一库一进程**（subprocess 隔离）。

**4. `argv[7]` 是 `TRACE_LIM` 不是布尔开关。**
`main.c:167` 把 `argv[7]` 直接当 `strtoull` 上限用。传 `"1"` 会把上限设成 1 条，
trace 只记 1 条就停 —— 一开始误以为「合并丢了 20617 条 PC」。
正确用法：`argv[7]=5000000`。
